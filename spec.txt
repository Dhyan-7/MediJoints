Executive product statement
Medi Joints is positioned as a real-time healthcare coordination layer that connects patients, hospitals, and healthcare authorities around the same capacity information. The core experience makes hospital bed availability discoverable on a map, supports temporary reservation, and provides an emergency SOS workflow. AI is the intelligence layer for triage, hospital recommendation, smart SOS routing, predictive availability, record summarization, multilingual assistance, surge prediction, and data-integrity monitoring.
What the web demo must prove
The problem is an information/coordination delay, not simply hospital discovery.
The patient sees availability by bed category rather than only hospital location.
The patient can move from discovery to an actionable reservation or SOS request.
A hospital receives the same event and can accept/prepare/respond.
A capacity change propagates visually across the network.
An authority can see network-wide capacity, SOS events, and surge/fraud signals.
AI is visibly useful without presenting it as a replacement for doctors.
The UI is calm, high-trust, fast, and usable under stress.

2. PRD — Product Requirements Document
2.1 Product vision
Create a world where no patient loses time searching for a hospital bed.
The product vision in the source material is to make hospital capacity as transparent and accessible as checking restaurant or hotel availability. The MVP demo should therefore behave like a familiar discovery-and-action product, while preserving healthcare-specific trust, emergency-first design, and role-based coordination.
2.2 Problem statement
Families may search for a hospital, then call multiple hospitals individually to discover whether the required capacity exists.
A phone confirmation can become stale before arrival.
Ambulance/paramedic teams may lack a unified capacity view.
Hospital internal information is not normally visible to patients.
Existing tools solve pieces—location, doctor booking, internal hospital operations—but do not provide the same real-time coordination loop.
Source evidence: The product document describes the problem as an information gap and explicitly frames the traditional journey as emergency → panic → hospital search → repeated calls → possible arrival failure. fileciteturn4file0L92-L119

Open Medi Joints patient dashboard.
Choose location or use demo location.
Select required bed type or care need.
Review map/list of nearby hospitals.
Open a hospital card and inspect availability, specialization, rating, ETA, and last update.

Confirm reservation.
Show Reservation ID and a visible temporary lock countdown.
Show navigation CTA and contact hospital CTA.

Acceptance: The journey must be completable without leaving the app, with a clear status after every action.
3.2 Patient: emergency SOS
Tap the persistent SOS CTA.
Show a short confirmation layer designed to prevent accidental triggers while keeping the flow fast.
Capture demo location and optionally selected symptoms/condition.
AI dispatcher ranks the top three suitable hospitals using condition match, required capacity, ETA, and response history.
Show hospitals being alerted in priority order.
Simulate a hospital acceptance.
Show accepted hospital, ETA, direct call CTA, and navigation CTA.
Show an emergency status timeline: SOS sent → hospital alerted → accepted → route active.
Safety copy: The demo must state that AI assists routing/triage and does not replace qualified medical professionals. This matches the pitch script's safety framing. fileciteturn4file2L815-L828
3.3 Hospital: respond to reservation
Hospital user opens dashboard and sees live bed counts.
A new reservation appears in Incoming Reservations.
Hospital opens the reservation and reviews required bed type, patient summary, ETA, and arrival time.
Hospital accepts the reservation.
The selected bed count changes to reserved.
Patient side receives a simulated confirmation.
Hospital can mark the bed as preparing / ready / occupied.
Acceptance: The hospital dashboard should make the operational value obvious: structured incoming flow, advance notice, and bed preparation.
3.4 Hospital: respond to SOS
SOS alert appears as high-priority notification.
Hospital sees patient location, condition, required capacity, ETA, and relevant medical summary.
Hospital can Accept SOS or Decline.
Accepting changes the patient-side status to Hospital Accepted.
Hospital can assign a bed/department and mark preparation started.

4. SRS — Software Requirements Specification
4.1 System overview
The showcase application is a front-end-first simulation of the Medi Joints ecosystem. It is structured as one responsive web application with role-specific workspaces. The production architecture described by the source documents includes a real-time database, push/WebSocket synchronization, GPS/maps, reservation engine, SOS trigger system, and analytics engine. For the showcase, these are represented by deterministic local state and simulated events.
Source evidence: The product document describes real-time synchronization as hospital update → instant sync → patient map/list update → reservation auto-lock → company/authority monitoring. fileciteturn4file0L264-L297

5. UX/UI Design Specification
5.1 Design direction
Visual tone: clinical, premium, calm, modern, trustworthy—not overly futuristic.
Primary composition: white/light surfaces, deep blue navigation, restrained teal/green for positive states, amber for limited states, red only for emergency/error.
Typography: highly legible sans-serif; use large headings and compact operational labels.
Cards: rounded 14–18 px corners, subtle borders/shadows, strong hierarchy.
Motion: short 180–350 ms transitions; avoid distracting animation in emergency mode.
Maps: large visual area for patients; compact analytical map for authority.
Emergency CTA: always visible, high contrast, unmistakable label 'SOS Emergency'.
Trust signals: 'Verified', 'Updated X min ago', capacity status, and AI rationale.

6. Component & Interaction Specification
6.1 Patient live map
Map occupies ~55–65% of desktop viewport; hospital list occupies ~35–45%.
Color-coded pins: green = available, yellow = limited, orange = very low, red = no beds, grey = offline/stale.
Pin click opens a bottom/side sheet instead of navigating away.
List cards mirror map state exactly.
Each card includes: hospital name, verification, distance, ETA, relevant bed availability, freshness, and action.
A top filter row supports bed type, distance, specialty, and 'Available now'.
A 'Recommended for you' AI strip can appear after triage.
Source mapping: These availability colors and hospital-card details are directly based on the product document. fileciteturn2file3L176-L198
6.2 Reservation component
Step indicator: 1 Bed type → 2 Patient details → 3 Review → 4 Confirmed.
Show a clear temporary-lock rule such as 'Demo reservation hold: 60:00'.
Show reservation ID after confirmation.
Show hospital notification state: 'Hospital notified'.
Show navigation and call actions.
Bed count must visibly decrease when the demo reservation is confirmed.
Source mapping: The source describes selection of bed type, review of patient details, temporary auto-lock, hospital notification, confirmation ID/directions, and automatic bed count update. fileciteturn2file3L194-L208
6.3 SOS component
Persistent red emergency CTA with text, not icon-only.
Confirmation should ask only essential information.
Use location and selected condition in the dispatch simulation.
Show a ranked list of three hospitals with explicit reasons.
Show dispatch sequence and acceptance.
After acceptance, keep call and navigation actions prominent.
Display a disclaimer: 'AI assists routing; medical decisions remain with healthcare professionals.'
Source mapping: The source AI dispatcher ranks the top three hospitals based on condition, profile, capacity, specialization, traffic/ETA, and response history. fileciteturn3file1L504-L519
6.4 Hospital bed management
Use category rows with Available / Reserved / Occupied / Total.
Provide quick increment/decrement controls and a prominent Publish Update button.
Show 'Last updated' and data freshness status.
When publishing a change, trigger a global demo event and show the patient/authority effect.
Use confirmation for unusually large changes to avoid accidental edits.
6.5 Authority analytics
Top KPI row: hospitals online, beds available, ICU available, active SOS, stale hospitals.
Network map with filters for city/district/bed category.
Active SOS queue with severity and response time.
Surge card with trend, geographic area, confidence label, and recommended operational actions.
Integrity panel with flags for stale updates and suspicious availability patterns.
Source mapping: Surge signals in the product include rapid bed decreases, SOS spikes, seasonal patterns, and unusual ward admission patterns. fileciteturn2file6L410-L425
6.6 Medical tourism UI
Keep medical tourism visually connected to the core product but clearly secondary to emergency care.
Use treatment-first search rather than hospital-first search.
Comparison cards should emphasize indicative cost range, accreditation, specialist experience, and international-patient support.
Consultation CTA should appear before travel booking.
Travel plan can show a vertical timeline: consultation → treatment plan → visa → flight → airport pickup → stay → treatment → recovery.

12. Final Design Principle
Design the demo so a judge can understand it without explanation.
The strongest visual story is not a collection of screens. It is one connected event moving through the network: a patient needs care → AI identifies urgency → Medi Joints finds the right capacity → hospital accepts → bed is held/prepared → patient is routed → authority sees the system-level event. Every major screen should reinforce that same story.
